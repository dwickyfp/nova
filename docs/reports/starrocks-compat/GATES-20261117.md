## Defects found and fixed

| Finding | Fix | Evidence |
| --- | --- | --- |
| `SHOW [CREATE] ROUTINE LOAD [TASK]` and `information_schema.routine_load_jobs` showed Kafka broker addresses to every role that may see the job; only security admins see connection details elsewhere | Rows name the connection (`kafkaConnection`, `"kafka_connection" = ...`), unknown brokers show `hidden`, SASL/SSL passwords masked; the map is read as the caller and fails closed | `test_routine_load.py`; live attempt 1 failed this step, attempt 2 passed |
| Task graph ids (`database.schema.name`) were kept in 64 octets: a task in a database with a longer name could be created but `EXECUTE TASK` answered "Could not queue task run", and `CREATE PIPE` there failed with a 500 | Revision 0058 widens `graph_id` in edges and graph runs to 514 octets; API validation follows | `test_metadata_tasks.py::test_graph_ids_hold_the_longest_qualified_task_name`; live: long-name task queued; pipes 21/21 |
| `POST /api/v1/backup/repositories` built a storage-URL repository with inline keys, which the W5 frontend refuses: the endpoint always failed | It takes a stage folder (`@stage/folder/`, optional `read_only`), runs with stage export allowed, and refuses storage URLs before the engine | `test_backup.py`; live backup API 6/6 |
| Two tests still asserted the pre-W2/W5 layering (guard refusing `INTO FILES` in export contexts; audit redaction through a raw `CREATE REPOSITORY`) | Retargeted to the same property at the owning layer: the SQL frontend refuses non-stage unload targets; audit redaction uses a native `FILES()` read with inline keys | `tests/eval/test_custom_sql_tools_trajectory.py`, `test_query_pre_engine_audit.py` |

A guard probe confirmed that with `allow_stage_export` every non-stage unload
target (`s3://`, `hdfs://`, `file://`, local paths, inline keys, broker
properties, CTE/UNION/INSERT-SELECT placements, comment-split clauses) is
refused by the SQL frontend before planning.
